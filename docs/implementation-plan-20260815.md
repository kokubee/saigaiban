# 災害板（saigaiban）実施計画

作成日: 2026-08-15  
対象リポジトリ: `/Users/kokubee/code2026/saigaiban`  
基準コミット: `382b1b7 feat: separate disaster board support navigation`  
状態: 実装前の計画。コード変更・D1変更・デプロイは、この計画の受入条件を確認してから行う。

## 1. 災害板の役割

災害板は、OpenNaviの場所台帳を正体の正本として読み込み、町ごとに「その場所を見た時点でどうだったか」を共有する板である。

- OpenNavi: 自治体・水道・送配電・避難所等の公式情報と場所台帳
- 災害板: 場所カード、現地で見た状況、店側の自己申告、地図への導線
- 公式判断: OpenNavi、自治体、事業者の一次情報を優先

災害板自身は、投稿があっても「公式に営業中」「公式に開設中」と言わない。自由チャット、人探し、個人宅への直接支援仲介、住所・電話・待ち合わせ情報は扱わない。

## 2. 現在の実装と不足

### できていること

- 都道府県→市区町村→場所カードの遅延読み込み
- OpenNavi `/api/board/meta`・`/api/board/places` のみを利用
- 未確認カード、見かけた人の報告、店側の自己申告
- `使えていた／制限があった／使えなかった／変わっていた` の状態
- Googleマップ検索URL、公式ハブ、公式支援ハブへの分離導線
- 投稿本文からURL・電話・連絡先・待ち合わせを拒否
- OpenNavi依存の短期キャッシュ基盤（既定はoff）

### 次に整えること

- 場所一覧に「いま必要なこと」の入口がなく、カテゴリ数が多い地域で迷いやすい
- `created_at` は表示するが、カード単位の stale 判定・観測時刻・確認時刻がない
- 投稿フォームが汎用的で、被災者が短時間で「今も使える／変わった」を送る説明が弱い
- 停電・断水はOpenNavi公式板への導線が中心で、災害板側の関連導線が目立たない
- オフライン時の読み取り、印刷、紙・電話へのフォールバックがない
- OpenNavi障害時の期限付きスナップショットと、依存APIの状態表示を明確化する必要がある
- 立ち上げ、投稿受付、収束、次災害への切替が一人の記憶に依存している

## 3. イマココナビから取り込むUX要件

公開画面の調査で有効だった要素だけを採用する。データ、投稿本文、ユーザー情報、件数の転載はしない。

| 要素 | 災害板での実装方針 |
|---|---|
| 地域→カテゴリ→カード | 市区町村ページに困りごとのクイックフィルタを追加 |
| 投稿時刻・最終確認 | 観測時刻と災害板が受信した時刻を分けて表示 |
| 「今も有効」「状況更新」 | 同じ場所の詳細ページで短い選択肢として提供 |
| 断水・停電の補足 | 公式はOpenNaviへ戻し、災害板は場所に紐づく観測だけを扱う |
| 個人の意見を控える注意 | フォーム前、入力欄、投稿後の3箇所で表示 |
| 開いている所だけ | 「営業中」ではなく「報告上、使えていた」と表現 |

## 4. 目標ユーザー体験

### 4.1 トップ

- 災害名と「ここは公式窓口ではない」を最上部に固定
- 都道府県・市区町村の選択を最初に行う
- OpenNavi公式ハブ、避難・医療・停電・断水の公式導線を常設
- 全地域の場所一覧をトップで取得しない（現行の遅延読み込みを維持）

### 4.2 市区町村ページ

市区町村を開いた直後に、次のクイックフィルタを表示する。

`避難・安全` / `水・給水` / `食事・物資` / `トイレ` / `給油・店` / `医療` / `洗濯・入浴` / `交通`

フィルタを選ぶと、該当カテゴリだけを取得・表示する。カードの上部には次を固定する。

1. 状態（未確認／報告あり／古い可能性）
2. 観測時刻・投稿時刻
3. 出典（台帳／店側自己申告／見かけた人）
4. 次の行動（地図、公式ハブ、いまどうかを書く）

### 4.3 場所カード・詳細

- 「未確認」を初期状態として残す
- 避難所カードには「台帳であり、開設中とは限らない」を表示
- `使えていた` は「見かけた人がその時点で使えていた」と表示
- 状態と時刻が古い場合は「古い可能性あり」を出し、「再確認する」を促す
- 投稿履歴は新しい順だが、公式情報へのリンクを常に先に置く
- ボタン・入力欄は44px以上、本文は16px以上を目標にする

### 4.4 空状態・障害時

「該当なし」だけで終わらせず、次を出す。

- この板に確認済み情報がないこと
- OpenNavi公式ハブへのリンク
- 自治体・事業者の公式確認先
- 電話、避難所掲示、紙で確認する案内
- OpenNaviの取得失敗時は「最新状態を取得できない」と明示

## 5. 投稿・鮮度・安全性の仕様

### 5.1 投稿の最小契約

- 場所ID: 必須。自由な場所名の新規作成はしない
- 立場: 見かけた人／自分の店・施設
- 状態: 使えていた／制限があった／使えなかった／変わっていた
- 観測時刻: 送信時刻を自動記録し、将来「今／○時ごろ」を追加可能にする
- メモ: 事実のみ、80字以内。URL・電話・氏名・住所・待ち合わせは禁止

### 5.2 stale判定

提案する初期ルール:

- 24時間以内: 通常表示
- 24〜72時間: 「古い可能性あり」
- 72時間超: 一覧の先頭から下げ、公式確認と再報告を促す

災害の種類・カテゴリごとに期限を変更できるよう、定数を `src/reports.ts` から分離する。期限切れで「閉店」「復旧」へ自動変更しない。

### 5.3 投稿制御

- IPハッシュ＋場所IDのクールダウンを維持
- 投稿停止、確認のみ、通常受付を環境・地域単位で切替可能にする
- 通報・非表示・管理者確認の経路を追加する
- 同じ内容の連続投稿をまとめ、最新1件だけをカード要約に出す
- 住所、電話、SNS ID、個人名、待ち合わせ、救助依頼を保存しない

## 6. 停電・断水の扱い

災害板にOpenNaviと別の「公式停電・断水データベース」を作らない。二重管理と誤表示を避けるため、役割を分ける。

### 災害板で行うこと

- 市区町村ページと場所詳細に、OpenNaviの停電・断水公式ページへのリンクを常設
- コンビニ、給水所、銭湯、病院などの場所カードに、見た時点の補足を受ける
- 「トイレが断水で使えない」「生活用水が使えた」など、場所に紐づく事実メモを許可
- 報告は公式状態に昇格させず、観測時刻と「公式ではない」を表示

### OpenNaviへ戻すもの

- 地域全体の停電・断水状況
- 復旧見込み、影響軒数、給水車の公式発表
- 自治体・水道事業者・送配電事業者の最新情報

将来、地域全体の住民報告を災害板にも持たせる場合は、別設計（保持期間、地区粒度、相反報告、管理者責任）として承認を取る。今回の実装では場所カード報告に限定する。

## 7. 実装フェーズ

### P0 — 仕様・計測・テスト基盤

対象: `src/types.ts`、`src/reports.ts`、`src/html.ts`、`test/core.test.ts`。

- `observedAt`、`createdAt`、`freshness` の公開表現を定義
- 公式／店側自己申告／見かけた人／未確認を共通ラベル化
- 市区町村、カテゴリ、カード、投稿完了、公式リンククリックを匿名計測
- WebレスポンスにOpenNaviの内部キーや非公開フィールドが混入しないテストを追加

受入条件: 現行の投稿制約を壊さず、既存テストを通過し、代表カードの状態・時刻・出典が一貫する。

### P1 — 被災者向け画面整理

対象: `src/html.ts`、CSS、`src/labels.ts`、`src/opennavi.ts`。

- 市区町村ページに困りごとフィルタ
- カード上部へ状態・時刻・出典を集約
- 停電・断水のOpenNavi公式導線を市区町村ページへ追加
- 低速回線で地図・外部画像を遅延表示
- キーボード、文字拡大、色だけに依存しない表示を確認

受入条件: iPhone相当／Android相当で、地域→困りごと→カード→次の行動が3タップ以内。0件でも公式ハブへ進める。

### P2 — 報告体験と鮮度

対象: `src/reports.ts`、`src/html.ts`、`migrations/`、`test/core.test.ts`。

- 観測時刻の入力・表示
- 24〜72時間のstale表示
- 「今もそう」「変わった」「復旧した」を短い選択肢で操作
- 投稿後に個人情報・連絡先を含まないことを再検査
- クールダウン、通報、非表示、管理者確認のテスト

受入条件: 古い報告が営業中・開設中と誤表示されず、報告が公式情報として表示されない。

### P3 — オフライン・依存障害

対象: `src/cache.ts`、`src/index.ts`、`src/html.ts`。

- OpenNaviの期限内スナップショットを、取得失敗時の読み取りフォールバックにする
- 「いつ取得したデータか」「最新ではない」を明示
- 投稿フォームは通信失敗時に完了扱いしない
- OpenNaviが落ちた場合も公式ハブURLと固定の安全案内を返す
- 印刷用の町ページ（公式リンク、緊急電話、時刻）を追加検討

受入条件: OpenNavi 5xx、タイムアウト、キャッシュなし、通信断をテストし、推測データを表示しない。

### P4 — 負荷・費用

対象: `src/cache.ts`、`src/opennavi.ts`、`src/index.ts`、`wrangler.jsonc`。

- 公開HTMLとOpenNavi依存GETのみ短期キャッシュ
- 投稿POST、場所詳細の個人状態、管理操作はno-store
- 市区町村ページの取得上限とページングを維持
- 秒単位ポーリング、WebSocket、常時地図更新は導入しない
- GA4・Cloudflare使用量を日次確認し、キャッシュ・投稿受付を停止できるフラグを用意

受入条件: ステージングで10／100／300 RPSを測定し、キャッシュヒット時p95 1秒以内、ミス時p95 2秒以内、5xx 0.1%未満を目標とする。

### P5 — 平時運用・次災害ドリル

対象: `README.md`、新規 `docs/next-disaster-runbook.md`、`wrangler.jsonc`。

- OpenNavi側の災害切替を前提に、災害板を別ドメインで立ち上げる手順を固定
- `準備 → 公開 → 投稿受付 → 監視 → 収束` の状態を記録
- 投稿受付の開始・停止、stale基準、通報対応、ロールバックをチェックリスト化
- 月1回、別県の設定でトップ→市区町村→カード→報告→収束を再現
- 収束後は投稿受付を止め、公開ページを公式確認先中心へ戻す

受入条件: 新しい県を仮定し、設定確認・テスト・デプロイ・本番リンク検査・投稿停止までを60分以内に再現できる。

## 8. 持続可能性・コスト

- Cloudflare Worker + D1 + 静的HTMLを基本とし、平時は固定費中心にする
- OpenNaviの公式リンクを利用し、Maps API・有料検索・チェーン自動取得を前提にしない
- 生成AIは災害板のリクエスト経路に置かない。説明文・分類は決定論的にする
- `PUBLIC_READ_CACHE=off / shadow / on` を使い、差分確認後にキャッシュを有効化する
- 1ページ表示がOpenNavi全地域の取得へ連鎖しないよう、市区町村単位の遅延読み込みを守る
- 月次でWorkerリクエスト、CPU、D1読取・書込、キャッシュヒット率を記録する
- 追加課金が発生する変更は、月額上限・停止条件・ロールバックを先に決める

## 9. 受入KPI

| 指標 | 初期目標 |
|---|---|
| 地域→次の行動 | 3タップ以内、20秒以内 |
| 公式導線 | 主要カテゴリから100%到達 |
| stale表示漏れ | 0件 |
| 公式でない投稿の公式表示 | 0件 |
| 個人情報・連絡先の保存 | 0件 |
| OpenNavi障害時の誤表示 | 0件 |
| 投稿受付停止の反映 | 5分以内 |
| 災害立ち上げドリル | 60分以内 |

利用者数が少なくても、必要なときに到達できること、誤情報を公式と誤認させないこと、次災害で再現できることを合格とする。

## 10. コミット単位

実装時は次の単位で分け、各コミットを個別に検証する。

1. `docs:` 計画・運用手順のみ
2. `feat(ui):` 市区町村フィルタとカード表示（DB変更なし）
3. `feat(report):` 観測時刻・鮮度・投稿制約（マイグレーションを含む場合は単独）
4. `feat(resilience):` OpenNavi依存キャッシュと障害フォールバック
5. `test:` E2E・負荷試験・次災害ドリル

各段階で `npm test`、`npm run typecheck`、公開URLのリンク検査を行う。災害板側の変更をOpenNaviリポジトリへ混ぜない。

## 11. 今回は実施しないこと

- イマココナビの投稿本文・ユーザー・件数の転載
- 公式情報の自動スクレイピング・自動掲載
- 投稿を公式状態へ自動昇格
- 地域全体の停電・断水データを災害板で二重管理
- 自由チャット、人探し、個人宅支援の仲介
- 常時位置追跡、秒単位のリアルタイム更新、緊急相談のAI処理
- OpenNavi側の設定・LINE・外部送信を、災害板の実装と同じコミットで変更

## 12. 実装開始条件

1. この計画を災害版リポジトリの正本として承認する
2. 投稿受付の地域・期間・保持期間を決める
3. iOS／Android実機確認者と、投稿通報の代替担当を決める
4. Cloudflare費用上限とアラート先を確認する
5. P0の状態語・鮮度基準・イベント名を確定する

承認後はP0から開始し、P1〜P5を段階的に実装する。公開キャッシュの有効化と投稿受付の再開は、別々のリリース判断とする。
