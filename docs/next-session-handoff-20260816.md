## 次に整える課題

### 1. 支援イベントの情報源と正本

- 自治体・社協・医療団体等の公式ページを一次ソースとする
- SNS検索で見つけた情報は、公式URL確認後にのみカタログへ投影する
- `物資配布`・`炊き出し`を一般の店舗カテゴリへ混ぜない
- OpenNaviの「外から支援する」情報と、災害版の「被災者が受け取る支援」を分ける

### 2. 被災者向け画面

- 市区町村ページに `避難・安全 / 水・給水 / 食事・物資 / 医療 / トイレ / 入浴` の絞り込みを追加
- 支援イベントカードに開催日時、場所、受付状態、確認日、公式リンクを表示
- 0件の場合も「現在確認できる情報なし」と公式確認先を表示
- Android/iPhoneの実機幅で、地域→カテゴリ→イベント→公式リンクを確認

### 3. 停電・断水の正本問題

`reports` は場所カード用であり、地域全体の停電・断水を混在させない。OpenNavi `/lifelines` の既存書き込み経路をlegacy/read-onlyまたは管理者専用にする方針が決まるまで、災害版の投稿受付は再開しない。

将来追加する場合は、`lifeline_reports` を別migration・別API・別保持期間で設計する。公式状態への自動昇格はしない。

### 4. 投稿再開の条件

投稿をONにしない。再開には次が必要。

1. write ownership（二重書き込みをしない正本）の承認
2. 本番D1 migrationの適用と実DB監査確認
3. Turnstile・短期HMAC・管理者認証の実設定確認
4. 地域allowlist、保存期間、通報対応担当の確定
5. Android/iPhoneで投稿・通報・停止を実機確認

未適用の `migrations/0004_legal_consent.sql` は、DBバックアップと適用承認なしに実行しない。

### 5. オフライン・障害時

- 災害板には、期限付きの明示スナップショットと印刷用ページがまだない
- OpenNaviが落ちたときは「最新状態を取得できない」と明示し、推測データを出さない
- 通信断時に投稿完了と誤表示しない
- 公式リンク、緊急電話、取得日時を紙・電話へつなぐフォールバックを検討する

### 6. 監視・通知

巡回失敗やOpenNavi依存APIの異常は、現状では記録中心で自動通知が未整備。次回は、異常件数・HTTP 403/404・timeoutを担当者へ通知する仕組みを別タスクとして設計する。通知先やsecretを推測して設定しない。
